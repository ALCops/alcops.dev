When `SetLoadFields`, `AddLoadFields`, or `SetBaseLoadFields` is used on a record variable that subsequently performs `Insert`, `Delete`, `Rename`, `TransferFields` or `Copy`, the platform must JIT-load all remaining fields before the operation can execute.

This causes two problems:

1. **Performance penalty**: The JIT load triggers an extra SQL roundtrip, making the code strictly slower than not using partial records at all (2 roundtrips instead of 1).
2. **Runtime errors**: Under concurrent access, the JIT load can fail with "Inconsistent read of field(s)" (when another user modifies the record between the initial load and the JIT load) or "JIT loading of field(s) failed" (when the record is deleted or renamed).

### Example

{{< highlight al "hl_lines=5" >}}
procedure DeleteItem(ItemNo: Code[20])
var
    Item: Record Item;
begin
    Item.SetLoadFields(Item."No."); // Partial records cause JIT load on full-field operations [PC0031]
    Item.Get(ItemNo);
    Item.Delete();
end;
{{< /highlight >}}

Remove the `SetLoadFields` call — since the record will be deleted, loading all fields upfront is correct:

{{< highlight al >}}
procedure DeleteItem(ItemNo: Code[20])
var
    Item: Record Item;
begin
    Item.Get(ItemNo);
    Item.Delete();
end;
{{< /highlight >}}

### Exception

The diagnostic is not raised for `Modify`, `ModifyAll`, `DeleteAll`, or `Init`. `Modify` only writes changed fields and does not trigger a JIT load. `ModifyAll` and `DeleteAll` are set-based operations and `Init` is an initialization operation — none of these require all fields to be loaded.

The diagnostic is also suppressed when the write operation is inside a conditional branch (`if`, `case`, `while`, `for`, `foreach`), because the write may only execute on a path where the record was not loaded via partial records. `repeat..until` loops are still flagged because the body always executes at least once.

Temporary record variables (no SQL backing, no JIT load) are skipped, and so is a record variable whose partial-records state is reset or handed off between the partial read and the write operation: `Clear()`, `Reset()`, `SetLoadFields()` without arguments, passing the variable by `var` to a procedure or event publisher, passing it to `Codeunit.Run`, `Page.Run` or a similar built-in, or calling a table procedure on it. The callee may reset the load selection, so the write is no longer known to JIT-load. Passing a `Record` variable by value does not suppress the diagnostic: the callee works on a copy with its own load selection. A `RecordRef` passed by value still refers to the same table instance, so it does suppress it.

The rule analyzes one procedure or trigger body and its local variables only. Global variables, parameters, flows through other procedures and event subscribers are not analyzed, because the record's load state is not visible there: which procedure ran first on a global, what the caller did before passing a parameter, or whether a publisher loaded the record partially cannot be determined statically, and procedures from a dependency have no body to inspect. A subscriber that needs additional fields of a record it receives should call `AddLoadFields` rather than `SetLoadFields`, which would overwrite the publisher's selection.
