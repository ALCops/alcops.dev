`XX0000` is an **internal diagnostic** shared by all ALCops analyzers: `AC0000`, `DC0000`, `FC0000`, `LC0000`, `PC0000`, and `TA0000`. It is reported when a rule throws an unhandled exception while analyzing your code. It does not indicate a problem in the analyzed object — it indicates a defect in the analyzer itself.

### Why this exists

When an analyzer throws an unhandled exception, the AL compiler normally reports it as the generic [`AD0001`](https://learn.microsoft.com/dynamics365/business-central/dev-itpro/developer/devenv-analyzer-restrictions) diagnostic at `app.json` line 1, with no indication of which object or line triggered the failure. That makes the culprit nearly impossible to locate.

Each ALCops analyzer wraps every analysis callback so that an unhandled exception is converted into its `XX0000` diagnostic **at the object or line being analyzed** instead. The message names the failing analyzer and the exception:

```
Analyzer 'SomeAnalyzer' threw an exception of type 'System.NullReferenceException': Object reference not set to an instance of an object.
```

### What to do

1. Note the object and line where the diagnostic is reported — that is the input that triggered the analyzer defect.
2. [Open an issue](https://github.com/ALCops/Analyzers/issues) with the analyzer name from the message, the exception type and message, and (if possible) a minimal AL snippet that reproduces it.

Analysis continues after the exception is reported; the failing rule simply produces no result for that object.

### Suppressing

`XX0000` diagnostics are informational and never break a build. If you need to silence one while a fix is pending, suppress it like any other diagnostic via the ruleset or a `#pragma warning disable` directive (e.g. `#pragma warning disable PC0000`).
