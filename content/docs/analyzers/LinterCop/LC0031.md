`LockTable()` does not acquire a lock. It marks the table so that every subsequent read of that table in the transaction — on *any* record variable — uses the SQL `UPDLOCK` hint for the remainder of the transaction. An event subscriber, a FlowField calculation, or unrelated code further down the call stack can end up locking rows it never intended to touch.

> When `Record.LockTable` is called on an `Item` record, all reads against that table will be done with the `UPDLOCK` hint, not just the variable it was called on.

— [Performance Articles for Developers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-developer) on Microsoft Learn

`ReadIsolation`, introduced in Business Central 2023 wave 1 (v22), sets the isolation level on the **specific record variable** only. Other variables of the same table remain unaffected. The two are not equivalent, and that difference is the point: `ReadIsolation` keeps lock scope tight and predictable.

There is a second reason to make the switch. [Tri-state locking](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-tri-state-locking) (default from v25 onward) falls back to pessimistic two-state locking the moment `LockTable()` is called anywhere in the transaction:

> Explicitly using the LockTable method in code maintains the same behavior, disabling optimistic reads.

— [Tri-state locking](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-tri-state-locking) on Microsoft Learn

Replacing `LockTable()` with `ReadIsolation` preserves tri-state benefits — fewer locks, higher concurrency, and fewer lock timeouts across the system.

### Example

The following procedure locks the entire `G/L Entry` table for the rest of the transaction just to read the last entry number:

{{< highlight al "hl_lines=5" >}}
procedure GetNextEntryNo(): Integer
var
    GLEntry: Record "G/L Entry";
begin
    GLEntry.LockTable(); // Use ReadIsolation instead of LockTable [LC0031]
    GLEntry.FindLast();
    exit(GLEntry."Entry No." + 1);
end;
{{< /highlight >}}

With `ReadIsolation`, only this specific variable acquires the lock. Any other code reading from `G/L Entry` later in the transaction remains unaffected:

{{< highlight al "hl_lines=5" >}}
procedure GetNextEntryNo(): Integer
var
    GLEntry: Record "G/L Entry";
begin
    GLEntry.ReadIsolation(IsolationLevel::UpdLock);
    GLEntry.FindLast();
    exit(GLEntry."Entry No." + 1);
end;
{{< /highlight >}}

### Convert or delete

The microsoft/BCQuality [coding guidance](https://github.com/nickaaron/BCQuality/tree/main/knowledge/performance) endorses `LockTable` only when a read directly precedes a dependent `Insert`, `Modify`, or `Delete`. Two questions decide what to do with a flagged call:

1. **Does a read of the same table follow in the transaction path this code controls?** If yes, convert: put `ReadIsolation(IsolationLevel::UpdLock)` on the instance that performs that read.
2. **Does no such read follow?** Then the lock is dead — delete the line.

The modern shape for "make sure nobody grabbed this number" is `ReadIsolation` on a second instance that reads. The Base Application's `Customer.Table.al` in `OnInsert` does this:

{{< highlight al "hl_lines=3" >}}
var
    Customer: Record Customer;
begin
    Customer.ReadIsolation(IsolationLevel::ReadUncommitted);
    while Customer.Get("No.") do
        "No." := NoSeries.GetNextNo(NoSeriesCode);
{{< /highlight >}}

The same pattern appears in `Vendor`, `Item`, `Contact`, `Employee`, `BankAccount`, `Resource`, and the 2025 Sustainability ESG tables.

### LockTable in table triggers

A bare `LockTable()` in `OnInsert` or `OnDelete` binds to the same built-in as `MyVar.LockTable()` and has the same transaction-wide effect. The compiler models no receiver-dependent semantics — all receiver forms resolve to one singleton built-in method.

Most trigger `LockTable()` calls in the Base Application are dead. Two representative shapes and their resolutions:

**Dead lock — no read follows.** A journal-batch `OnInsert` calls `LockTable()` then `Get()`s an unrelated template table. The lock on the journal line's own table serves no read. The Base Application removed it:

{{< highlight al "hl_lines=3" >}}
trigger OnInsert()
begin
    LockTable(); // [LC0031] — no read of this table follows; delete the line
    ItemJnlTemplate.Get("Journal Template Name");
    ...
end;
{{< /highlight >}}

**Live lock — a dependent read follows.** An entry table's `OnInsert` locks the table, then a second instance reads the last entry number. Convert the lock to `ReadIsolation` on the instance that reads:

{{< highlight al "hl_lines=3-4" >}}
trigger OnInsert()
var
    Attachment2: Record Attachment;
begin
    Attachment2.ReadIsolation(IsolationLevel::UpdLock);
    if Attachment2.FindLast() then
        "No." := Attachment2."No." + 1;
{{< /highlight >}}

The Base Application still contains about 78 such trigger calls, has removed two since BC 23.5 and added none. Its newer apps (Business Foundation, E-Document Core, Subscription Billing, Excise Taxes) contain no `LockTable` at all.

### Code fix

The **ALCops: Replace LockTable() with ReadIsolation** code fix rewrites the call to `ReadIsolation(IsolationLevel::UpdLock)` on the same receiver, including bare `LockTable()` inside a table or tableextension. It drops `Wait`/`VersionCheck` arguments because `ReadIsolation` has no equivalent parameters.

The fix never deletes — it always converts. Use it only when a dependent read follows; when the call is dead, delete the line manually.
